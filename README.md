# ShieldEdge: On-Device Threat, Phishing & Scam Detection

**Bharat AI-SoC Student Challenge 2026–27 · Problem Statement 3: Cybersecurity & Digital Safety**

ShieldEdge checks **links, SMS messages and network flows** for phishing, scams and intrusions **entirely on
the device**. Nothing is sent to the cloud. When it finds a threat, **Llama 3.2 1B-Instruct runs locally
through ExecuTorch** (INT4, XNNPACK) and explains the problem in plain language. A vetted playbook then tells
the user what to do, with Indian reporting channels such as 1930, cybercrime.gov.in and Sanchar Saathi.

```
 URL / SMS / flow CSV / QR image
            │
            ▼
 ┌─────────────────────────── DETECTION  (deterministic, 3–13 ms) ──────────────────────────┐
 │ URL : char + word n-gram LR + 22 structural features → gradient boosting; official-domain│
 │       allowlist, brand-misuse and free-hosting rules                                     │
 │ SMS : word + char TF-IDF, calibrated LinearSVC; link, transactional and Hinglish rules   │
 │ Flow: kNN novelty score on 18 CICFlowMeter statistics (trained on benign traffic only)   │
 └──────────────────────────────────────────┬───────────────────────────────────────────────┘
                                            ▼
 DECISION ENGINE ─ SAFE → done (no LLM).  Otherwise: build *sanitised* evidence
                   (verdict, confidence, hostname/flow summary, signals; never raw SMS text)
                                            ▼
 ADVISORY ─ Llama 3.2 1B-Instruct, INT4 .pte, ExecuTorch llama_main + XNNPACK (Arm CPU)
            writes 2–3 sentences → validator (no invented links/numbers, no verdict
            contradiction) → else template.  Remediation always from the vetted playbook.
                                            ▼
 OUTPUT ─ verdict + explanation + steps;  local SQLite log stores SHA-256 hashes only
```

**Hardware:** Raspberry Pi 5 (4× Arm Cortex-A76, 8 GB), CPU only, no GPU/NPU and no internet connection.

**Llama never decides the verdict.** It only explains. If the runner is missing, slow or produces bad
output, the user still gets the verdict and a template explanation.

## Results (all numbers measured and reproducible)

Measured on two devices: the development laptop (**Intel Core i5-1235U, x86_64, 15 GB RAM, Ubuntu 24.04**) and a
**Raspberry Pi 5** (**4× Arm Cortex-A76 @ 2.4 GHz, 8 GB RAM, Ubuntu 24.04 arm64**). Detection quality is identical
on both, because the models and decision rules are the same and deterministic. Pi outputs are in
[`results/raspberry-pi-5/`](results/raspberry-pi-5/); setup is in [docs/PI_DEPLOYMENT.md](docs/PI_DEPLOYMENT.md).
Source: [`results/benchmarks.md`](results/benchmarks.md), generated by `models/evaluate_models.py`.

### Detection quality (held-out data, deployed decision path, positive = any warning)

| Task | Test set | Samples (threats) | Precision | Recall | F1 | FPR | ROC-AUC |
|---|---|---|---|---|---|---|---|
| URL phishing | Mitake held-out, **unseen domains**, max 50 URLs/site | 122,149 (43,265) | 92.9% | 95.9% | 0.944 | 4.0% | 0.992 |
| URL phishing | same test set, `PHISHING` verdicts only (strict) | 122,149 (43,265) | 98.4% | 89.2% | 0.936 | 0.8% | – |
| URL phishing | India challenge set (curated) | 65 (30) | 90.9% | 100% | 0.952 | 8.6% | 0.998 |
| SMS scam | **Real smishing 2022–25** held-out (IMC public reports + Mishra & Soni) | 1,510 (1,045) | 99.4% | 93.1% | 0.961 | 1.3% | 0.994 |
| SMS scam | Indian SMS, AI-generated, 7 languages (held-out 40%) | 632 (319) | 87.2% | 91.8% | 0.895 | 13.7% | 0.942 |
| SMS scam | UCI SMS Spam held-out, deduplicated (UK, 2011) | 1,034 (131) | 85.8% | 92.4% | 0.890 | 2.2% | 0.986 |
| SMS scam | India SMS test set (team-authored) | 60 (30) | 100% | 100% | 1.000 | 0.0% | 1.000 |
| Network anomaly | CIC-IDS-2017 **Friday** (trained on Monday benign) | 32,736 (12,736) | 96.2% | 99.9% | 0.980 | 2.5% | 0.992 |

Network detection rate by attack type: **DDoS 100%, Botnet C2 100%, Botnet (attempted) 100%, PortScan 99.6%**,
with 2.5% of Friday's benign flows flagged. The India sets are small and partly team-authored, so treat them as
sanity checks.

**Baselines on the same test sets** (from `models/evaluate_models.py`):

| Detector | Previous model | Current model | What changed |
|---|---|---|---|
| Network | Isolation Forest: F1 0.759, **DDoS 0%, Botnet C2 1.5%** | kNN novelty: **F1 0.980**, DDoS 100%, C2 100% | DDoS/C2 flows are ordinary feature by feature, but no benign flow has the same *combination*; the nearest-neighbour distance sees that, the forest's axis-aligned splits do not |
| SMS | trained on UCI (UK, 2011) + 70 team messages: real smishing F1 0.680 (**catches 51%**), Indian F1 0.782 (**29% false alarms**), UCI F1 0.958 | adds 10k real 2022–25 smishing reports, synthetic genuine service SMS and Indian code-mixed SMS: real smishing **F1 0.961 (93%)**, Indian **F1 0.895 (13.7%)**, UCI F1 0.890 | the old model only knew 2011 UK spam. Modern scams ("hi mum, new number", KYC, parcel fees) look different. The cost: more casual UK chats are flagged (UCI false alarms 0.6% → 2.2%), because modern "wrong number" scams deliberately sound like chat |
| URL | char n-grams, 157k URLs: F1 0.939, recall 94.9% | char + word n-grams, 315k URLs: **F1 0.944, recall 95.9%** | same false-positive rate; word tokens (`login`, `secure`, brand names) plus twice the data |

Models were chosen on validation data or cross-validation, except the network model: only Monday (benign) and
Friday (attacks) are available, so the Isolation Forest vs kNN comparison was made on Friday. Both are reported. The
kNN result does not hinge on a single feature: removing any one of the 18 features, including the TCP window size
(a known CIC-IDS-2017 artefact), keeps DDoS detection at 100%. Botnet detection does lean on its unusual service
port (8080).

### Why some numbers are lower than in earlier versions of this repo
Earlier versions reported numbers that were inflated by data leakage. We fixed the evaluation:
- **URL:** we now split by a fixed hash of the registered domain and keep at most 50 URLs per site. With a random
  split, 52% of test URLs shared a website with training data. Without the cap, one ad-tracking domain
  (`doubleclick.net`, ~3,000 near-identical URLs) alone moved the test false-positive rate by about 5 points
  depending on which split it fell into. An earlier "1.5% FPR" figure came from a split that happened to contain no
  such site.
- **SMS:** 403 duplicate messages are removed before the split, and 3,748 training messages that match a
  validation or test message in any dataset (the Mishra & Soni set partly overlaps UCI) are dropped.
- **Network:** benign test traffic now comes from a different day than training.

### On-device Llama (ExecuTorch, 10 runs, mean ± std) — laptop

| Program | Size | Load | Time to first token | Prefill | Decode | Full explanation | Peak RAM |
|---|---|---|---|---|---|---|---|
| `llama3_2_1b_int4.pte` (8da4w, g128, 4-bit embeddings) | 765 MB | 1.89 ± 0.07 s | 1.71 ± 0.11 s | 113 ± 3 tok/s | 34.0 ± 0.5 tok/s | 3.8 ± 0.2 s | 1.08 GB |
| `llama3_2_1b.pte` (bf16 baseline, 3 runs, earlier 343-token prompt) | 2.4 GB | 0.04 s | 191 ± 18 s | 1.8 ± 0.1 tok/s | 1.3 ± 0.0 tok/s | 264 ± 19 s | 2.52 GB |

Per token, INT4 is **63× faster at prefill and 26× faster at decoding**, and uses **2.3× less RAM** than the earlier bf16
export. Together with a shorter prompt, a full explanation went from about 4.4 minutes to under 4 seconds. INT4
loading takes longer because XNNPACK repacks the weights.

### On-device Llama — Raspberry Pi 5 (ExecuTorch `llama_main` built natively for aarch64, XNNPACK + Arm KleidiAI)

Same `llama3_2_1b_int4.pte` file as on the laptop (copied, not re-exported). 10 runs after warm-up, mean ± std.

| CPU threads | Load | Time to first token | Prefill | Decode | Full explanation | Peak RAM |
|---|---|---|---|---|---|---|
| 4 | 2.69 s | 1.68 ± 0.16 s | 116 ± 6 tok/s | 11.9 ± 0.1 tok/s | 8.1 ± 0.9 s | 1.08 GB |
| **2 (default on Arm)** | 2.68 s | 2.54 ± 0.19 s | 76 ± 1 tok/s | **14.5 ± 0.5 tok/s** | **7.8 ± 0.7 s** | 1.08 GB |
| 1 | 2.68 s | 4.52 ± 0.29 s | 43 ± 0 tok/s | 15.4 ± 0.3 tok/s | 9.5 ± 0.7 s | 1.08 GB |

**Arm tuning finding:** on the Pi 5, decoding is limited by memory bandwidth, so extra threads add synchronisation
cost. Decode is *faster* with 2 threads than with 4 (14.5–14.9 vs 11.9 tok/s), while prefill still benefits from more
threads. Two threads give the shortest full explanation, so ShieldEdge uses 2 threads on Arm by default
(`SHIELDEDGE_LLM_THREADS` overrides). The laptop decodes about 2.3× faster (34 tok/s).

**Other Pi measurements**
- **Detection latency per input:** URL 8.4 ms, SMS 5.6 ms, one network flow 10.9 ms. The Python process with all
  three detectors loaded uses 325 MB. The trained detector model files total about 13 MB.
- **Thermals:** 49.6 °C after the full benchmark, and the throttle flags stayed at 0x0 (never throttled), without
  a fan.
- **Offline proof** ([`offline_proof.txt`](results/raspberry-pi-5/offline_proof.txt)): Wi-Fi and Ethernet were down
  and `ping 8.8.8.8` failed. A full SMS analysis with a Llama explanation then ran with no sockets held by ShieldEdge
  or `llama_main`, and **0 packets** were captured by tcpdump on any interface.

Explanation quality on 19 flagged real detector outputs, including 3 prompt-injection attempts: **18/19 (95%) passed
validation** on the laptop and **17/19 (89%)** on the Pi, where outputs differ slightly. On both devices, 0 raw
inputs leaked into the prompt and every injection attempt kept its SCAM/PHISHING verdict. Rejected outputs (naming "Amazon" for `amaz0n-offers.shop`, plus one empty list-style answer on the Pi) were
replaced by the template explanation (`results/prompt_eval_*.json`).

## Quick start

```bash
git clone https://github.com/harmank18/shieldedge.git && cd shieldedge
./setup.sh                      # venv + requirements (QR scanning also needs: sudo apt install libzbar0)
source venv/bin/activate
```

The trained detector models are in the repo. For the Llama step you also need `executorch/llama_main` and
`executorch/llama3_2_1b_int4.pte` (from `executorch/export_llama.sh`, see below). Without them, ShieldEdge
automatically uses the template explanation.

```bash
python shieldedge.py --url "http://sbi-net-banking-update.xyz/login"          # streams the Llama explanation
python shieldedge.py --url "https://netbanking.hdfcbank.com/netbanking/"      # official domain → SAFE
python shieldedge.py --sms "Aapka SBI khata band ho jayega. Turant KYC update karo: http://sbi-kyc-help.xyz"
python shieldedge.py --sms "Rs.2,500.00 debited from A/c XX4521 to VPA zomato@icici. Not you? Call 18002586161 -HDFC Bank"
python shieldedge.py --flows data/samples/demo_flows.csv                      # 20 real CIC-IDS-2017 flows
python shieldedge.py --qr path/to/qr.png                                      # decode QR, analyse its URL
python shieldedge.py --url "..." --fast                                       # skip Llama (template only)

python shieldedge.py --alerts            # local audit log (hashes only)
python shieldedge.py --mark-safe 12      # report alert #12 as a false positive
python shieldedge.py --clear-logs        # delete all stored alerts
python shieldedge.py --web               # web dashboard on 127.0.0.1:8080 (see below)
python shieldedge.py --dashboard         # terminal dashboard
python shieldedge.py --serve             # REST API on 127.0.0.1:5050 (local only)
python shieldedge.py --benchmark         # detector latency on this device
```

### Web dashboard

`python shieldedge.py --web` starts a local dashboard. It is served by the device itself with no external
libraries or CDNs, so it works fully offline. It binds to 127.0.0.1; to watch the Pi's dashboard from a laptop, use
an SSH tunnel: `ssh -L 8080:localhost:8080 <pi>` and open http://localhost:8080.

- **Live feed and threat detail:** every item the detectors analyse, colour-coded. Click one to see its signals,
  stream the Llama 3.2 1B explanation from ExecuTorch (with TTFT and tok/s), and read the vetted playbook steps.
- **Labelled dataset replay** (`--no-replay` turns it off): real CIC-IDS-2017 Friday flows in a scripted scenario
  (normal → port scan → DDoS → botnet), plus held-out URLs and SMS never used in training, at 5 flows per second.
  Every replay item shows its dataset label and whether the verdict agrees, so mistakes are visible too.
  `data/build_dashboard_replay.py` rebuilds these files.
- **Network traffic chart:** flows and flagged flows per second over the last 2 minutes.
- **Try it:** analyse any link or SMS typed into the page. It is stored as a hash only.
- **On-device panel:** per-core CPU load, temperature, RAM, whether `llama_main` is running, and the number of
  external network connections held by the ShieldEdge process (0).
- **Model quality and audit log:** held-out metrics read from `results/`, plus mark-safe and clear-all-logs.

On the Raspberry Pi 5 the dashboard process uses about 336 MB. One explanation from the dashboard (SMS scam case)
took 2.7 s to load the model, 2.6 s to the first token, then 95 tokens at 13.3 tok/s, and passed the output
validator. Screenshot from the Pi (captured with live streaming off, so the feed is empty):
[docs/dashboard_pi5.png](docs/dashboard_pi5.png).

### Reproduce everything

```bash
python data/download_datasets.py           # Mitake URLs, UCI SMS, CIC-IDS-2017 (public datasets)
python models/train_url_classifier.py      # ~4 min on the laptop
python models/train_sms_classifier.py
python data/build_network_dataset.py && python models/train_network_detector.py
python models/evaluate_models.py           # → results/evaluation_results.csv, results/benchmarks.md
python scripts/benchmark_llm.py            # → results/llm_benchmark_<device>_<program>.json/.md
python scripts/prompt_eval.py              # → results/prompt_eval_<device>.json
pytest                                     # 45 tests
```

### Export Llama 3.2 1B-Instruct to ExecuTorch

Accept the Meta Llama 3.2 licence and place the original checkpoint in `models/Llama-3.2-1B-Instruct/original/`. Then run:

```bash
EXECUTORCH_DIR=~/executorch ./executorch/export_llama.sh        # INT4 8da4w + XNNPACK → executorch/llama3_2_1b_int4.pte
QUANT=bf16 EXECUTORCH_DIR=~/executorch ./executorch/export_llama.sh   # optional bf16 baseline
```

Build `llama_main` with `make llama-cpu` in the ExecuTorch v1.6.0 tree, and copy it and `libllama_runner.so` into
`executorch/`. On a Raspberry Pi, `scripts/setup_pi.sh` does this for you.

## Limitations

- **URL:** lexical analysis only (no WHOIS, page content or blocklist, by design for offline use). At the "any
  warning" level, 4% of benign test URLs get at least SUSPICIOUS (0.8% get PHISHING). Phishing on
  reputable shared platforms and brand-new lookalike domains with clean structure can be missed. The official-domain
  allowlist covers about 45 brands and government sites and needs maintenance.
- **SMS:** Indian and code-mixed coverage comes mostly from **AI-generated** messages, tested on held-out messages
  from the same generator, so the 0.895 there is optimistic for real Indian SMS. Even so, 13.7% of those genuine
  look-alikes are flagged. More casual chats are flagged than before (2.2% on UCI), because modern "wrong number"
  scams imitate chat. Real Indian scam and genuine SMS collected with consent would be the most valuable addition.
- **Network:** per-flow analysis of pre-captured CICFlowMeter CSVs only, with no live capture in Phase 1. The model
  is trained and tested on one testbed (CIC-IDS-2017); its 2.5% benign alarm rate and the botnet result (which uses
  the C2 port) need validation on other networks. This Hugging Face copy has no usable timestamps, so timing
  features (beaconing, per-second rates across flows) are not used.
- **Llama:** a 1B model's explanations are sometimes generic. The validator blocks invented contacts and links but
  cannot judge every phrasing. Remediation advice is therefore never generated by the model.
- **Benchmarks:** the Pi was powered by a USB-C phone charger rather than the official 27 W supply. No throttling
  was recorded, but numbers with the official supply and active cooler may differ slightly.

## Privacy, safety and legal notes

- **Offline:** no network calls during analysis. `scripts/offline_proof.sh` records a tcpdump capture during
  inference with the network disconnected.
- **Data minimisation:** the SQLite log stores a SHA-256 hash of each input, the verdict, the confidence and user
  feedback, never the SMS or URL text. `--clear-logs` deletes everything. The REST API listens on 127.0.0.1 only.
- **Advisory only:** ShieldEdge warns and never blocks. The user decides.
- **Network capture warning:** capturing traffic on networks you do not own or have written permission to monitor
  may be an offence under the **Information Technology Act, 2000 (Section 66 and related provisions)**. Only
  analyse traffic from your own network or the public CIC-IDS-2017 dataset.
